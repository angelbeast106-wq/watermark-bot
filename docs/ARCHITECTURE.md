# Архитектура Telegram watermark bot

## Назначение

Бот принимает изображение от пользователя, накладывает PNG-логотип как водяной знак, дает быстро поправить результат inline-кнопками и отправляет финальный JPEG файлом.

## Текущая структура

- `bot.py` - Telegram-слой: конфигурация, роуты aiogram, пользовательские сессии, загрузка файлов, отправка превью и результата.
- `watermark_processor.py` - доменная логика обработки изображений: EXIF-поворот, зеркалирование, масштабирование водяного знака, расчет позиции и JPEG-рендер.
- `.env.example` - шаблон переменных окружения.
- `assets/` - ожидаемое место для `watermark.png`.
- `requirements.txt` - runtime-зависимости.

## Поток обработки

1. Пользователь отправляет фото или image-документ.
2. `bot.py` скачивает файл из Telegram в память.
3. Для пользователя создается `Session`:
   - исходные `image_bytes`;
   - `TransformState` с текущим сдвигом и флагом зеркалирования.
4. `send_preview()` вызывает `render_watermarked_image()`.
5. `watermark_processor.py`:
   - открывает изображение через Pillow;
   - применяет `ImageOps.exif_transpose`;
   - при необходимости зеркалит изображение;
   - загружает и масштабирует watermark;
   - рассчитывает позицию по anchor, margin и offset; базовая позиция проекта - верхний правый угол;
   - композитит watermark поверх изображения;
   - возвращает JPEG bytes.
6. Бот отправляет превью с inline-клавиатурой.
7. Callback-кнопки меняют `TransformState` и перерисовывают превью.
8. По `Готово` бот рендерит финальный файл, отправляет `watermarked.jpg` и удаляет сессию.

## Основные сущности

### `Session`

In-memory состояние одного пользователя. Сейчас ключом служит `user_id`, поэтому у пользователя может быть только одна активная картинка.

### `WatermarkSettings`

Настройки наложения логотипа:

- путь к watermark-файлу;
- базовая позиция;
- ширина watermark в процентах от ширины изображения;
- отступ от края;
- отдельный верхний отступ для прижатия логотипа к верхнему краю;
- прозрачность.

### `TransformState`

Изменяемое состояние редактора:

- `offset_x` - горизонтальный сдвиг watermark в пикселях;
- `mirrored` - зеркалировать ли исходное изображение.

## Границы ответственности

`bot.py` не должен знать деталей Pillow-рендера. Его задача - принять Telegram-событие, обновить состояние и передать байты изображения в процессор.

`watermark_processor.py` не должен зависеть от Telegram, aiogram, пользователей или callback-кнопок. Это чистая функция поверх bytes/settings/state, что делает модуль хорошей целью для unit-тестов.

## Хранение состояния

Сейчас состояние хранится в процессе:

```python
sessions: dict[int, Session] = {}
```

Это простое решение для single-process polling. Ограничения:

- состояние теряется при рестарте;
- нельзя горизонтально масштабировать несколько процессов без общего хранилища;
- нет TTL/очистки забытых сессий;
- пользователь не может параллельно редактировать несколько изображений.

Если бот станет рабочим сервисом с нагрузкой, следующий шаг - вынести сессии в Redis или другое внешнее хранилище и добавить срок жизни.

## Ошибки и наблюдаемость

Сейчас есть базовый `logging.basicConfig(level=logging.INFO)`, но обработка ошибок точечная:

- пустой `BOT_TOKEN` приводит к `RuntimeError`;
- отсутствующий watermark возвращает сообщение пользователю;
- `TelegramBadRequest` при редактировании превью приводит к отправке нового сообщения.

Перед продуктивным запуском стоит добавить:

- структурированные логи для входящих изображений, callbacks и ошибок рендера;
- обработчик неожиданных исключений;
- ограничение размера входных файлов;
- понятные пользовательские сообщения для неподдерживаемых изображений.

## Точки расширения

Ближайшие доработки хорошо ложатся в текущую архитектуру:

- вертикальный сдвиг watermark;
- выбор позиции watermark кнопками;
- настройка размера/прозрачности пользователем;
- несколько watermark-шаблонов;
- сохранение результата в исходном формате, если это нужно;
- unit-тесты для `_calculate_position()` и `render_watermarked_image()`;
- сервисный слой с TTL-сессиями.

## Риски текущей версии

- `F.document.mime_type.startswith("image/")` может упасть, если у документа нет `mime_type`.
- Все изображения и результаты держатся в памяти.
- Нет проверки валидности env-значений.
- В репозитории нет `assets/watermark.png`, без него бот не сможет рендерить результат.
- Нет тестов и CI.
